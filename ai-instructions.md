# Инструкция для AI: формат JSON-патчей

Этот документ описывает формат JSON, который принимает приложение GitHub Repos Editor
для применения изменений к файлам репозитория.

## Как этим пользоваться

1. Передайте этот файл ИИ вместе с содержимым файлов, которые нужно изменить.
2. ИИ отвечает JSON-ом по описанному ниже формату.
3. Сохраните ответ ИИ в файл `patches.json`.
4. В приложении откройте репозиторий → кнопка **🤖 AI** → **📂 Загрузить JSON**.
5. Просмотрите превью, снимите галочки с ненужных операций, нажмите **Применить**.

## Общая структура

```json
{
  "version": 1,
  "changes": [
    { "type": "...", "path": "...", ... }
  ]
}
version — всегда 1.

changes — массив операций. Применяются сверху вниз.

Типы операций
1. replace — заменить первое вхождение
Заменяет первое вхождение строки find на replace. Если find встречается
больше одного раза — операция не выполнится (нужно уникальное совпадение).

json
{
  "type": "replace",
  "path": "js/main.js",
  "find": "let counter = 0;",
  "replace": "let counter = 0;\nlet attempts = 0;",
  "comment": "добавить счётчик попыток"
}
comment — необязательный, для человека.

2. replaceAll — заменить все вхождения
Заменяет все вхождения find на replace.

json
{
  "type": "replaceAll",
  "path": "styles.css",
  "find": "color: #ffffff;",
  "replace": "color: #fafafa;"
}
3. create — создать новый файл
Создаёт файл. Если файл уже существует — операция не выполнится.

json
{
  "type": "create",
  "path": "js/utils/helpers.js",
  "content": "export function sum(a, b) {\n  return a + b;\n}\n"
}
4. fullContent — заменить содержимое файла целиком
Перезаписывает весь файл. Полезно, когда правок много и проще отдать новую версию.
Если файла нет — он будет создан.

json
{
  "type": "fullContent",
  "path": "js/config.js",
  "content": "export const TIMEOUT = 5000;\nexport const RETRIES = 3;\n"
}
5. delete — удалить файл
json
{
  "type": "delete",
  "path": "js/legacy/old.js",
  "comment": "устаревший модуль"
}
Правила формирования find и replace
find — точная подстрока. Все пробелы, отступы, знаки — один в один как
в исходном файле. Если ошибётесь на один символ — патч не применится.

find должен быть уникальным в файле. Если фрагмент встречается
несколько раз — добавьте в find больше контекста (соседние строки),
чтобы выделить нужное место, или используйте replaceAll.

Переводы строк — \n (LF). В JSON-строке пишется как \n, не как
реальный перенос строки. Все файлы в репозитории используют LF.

Отступы — как в исходном файле. Обычно 2 пробела для JS/CSS/HTML,
4 пробела для C#. Пробелы, не табы.

replace содержит только то, на что меняется find. Не дублируйте
контекст — он уже в find.

Несколько правок в одном файле — оформляются как несколько элементов
в changes, а не как один с многострочным find.

Порядок операций важен. Если две операции касаются одного файла,
вторая видит файл уже после первой.

Полный пример
json
{
  "version": 1,
  "changes": [
    {
      "type": "replace",
      "path": "js/main.js",
      "find": "import { showBusy, hideBusy } from \"@ui/busy.js\";",
      "replace": "import { showBusy, hideBusy, updateBusyText } from \"@ui/busy.js\";",
      "comment": "добавить updateBusyText в импорт"
    },
    {
      "type": "replace",
      "path": "js/main.js",
      "find": "  showBusy(\"Обновление локальной копии…\");",
      "replace": "  showBusy(\"Обновление локальной копии…\");\n  console.log(\"pull started\");",
      "comment": "логирование старта pull"
    },
    {
      "type": "create",
      "path": "js/api/notes.js",
      "content": "export const NOTES_VERSION = 1;\n"
    },
    {
      "type": "delete",
      "path": "js/legacy/deprecated.js"
    }
  ]
}
Что увидит пользователь
При загрузке JSON в приложении:

✓ зелёная галочка — операция готова к применению.

⚠ жёлтая — применится, но с оговоркой (например, replaceAll найдёт
несколько совпадений, или создаётся файл, которого не было).

✗ красная — операция не применится. Причина указывается рядом:

«файл не найден»;

«'find' не найден в файле»;

«'find' встречается N раз — нужно уникальное совпадение»;

«бинарный файл — патч не поддерживается»;

«файл уже существует» (для create).

При ошибке пользователь может скопировать неуспешные операции и вернуть их
вам для исправления.

Чего делать нельзя
Не используйте номера строк. Приложение не работает со строками,
только с содержимым.

Не используйте unified diff. Формат @@ -10,3 +10,5 @@ не поддерживается.

Не давайте find без контекста, если фрагмент не уникален. Патч
провалится.

Не перезаписывайте бинарные файлы (png, jpg, pdf) через fullContent
или replace. Только delete и create доступны для не-текстовых файлов.

Если не уверены в точном find
Запросите у пользователя содержимое файла или его фрагмент и постройте find
на основе того, что видите. Не угадывайте.

## Как работать с картой проекта

К этому файлу приложена карта проекта — `project-map.md`. Из неё ты узнаёшь:

- структуру папок и файлов;
- какие модули есть в проекте;
- какие функции они экспортируют (только сигнатуры, без реализации);
- от каких модулей зависит каждый файл.

### Порядок работы

1. Прочитай карту проекта — найди в ней модули, относящиеся к задаче.
2. Если нужен точный текст фрагмента — **запроси у пользователя содержимое конкретного файла**.
3. Не проси прислать весь репозиторий целиком — это излишне и замедляет работу.
4. Формируй патч на основе реального содержимого файла, а не догадок.

### Когда запрашивать файл

Запрашивай файл, если:

- нужно понять, как именно выглядит функция внутри;
- нужен уникальный `find` — точная подстрока из реального кода;
- в карте видна только сигнатура, а для патча нужен контекст (окружающие строки).

### Как формулировать запрос

Пример:

> Пришли, пожалуйста, содержимое файла `js/ui/ai-modal.js`.

Если файлов нужно несколько — перечисли их списком. Приоритет: 1–3 файла, а не всё подряд.

### Если патч не применился

Пользователь может прислать тебе JSON с неуспешными операциями. В ответ:

1. Разберись, почему `find` не найден — обычно лишний или недостающий пробел, либо другой перевод строки.
2. Перепроверь по присланному пользователем содержимому файла.
3. Выдай исправленный JSON.

### Чего делать не нужно

- Не проси пользователя присылать **все** файлы проекта.
- Не генерируй патчи по памяти, если карта могла обновиться.
- Не используй `replaceAll`, если хочешь заменить конкретное место — сначала добавь контекста в `find`.
- Не пиши `find` размером в одну короткую строку типа `return;` или `}` — скорее всего, она не уникальна.

### Полезные подсказки по архитектуре

- В проекте есть **слои**: `core` (низкий уровень), `api` (работа с GitHub), `ui` (компоненты), `screens` (экраны).
- Если задача про интерфейс — файл будет в `ui` или `screens`.
- `main.js` — оркестратор, здесь собрана вся склеивающая логика. Если правка в нём — держи в голове, что функция вызывается из нужного слоя.
- Все внешние зависимости (`Octokit`, `idb-keyval`, `diff`, `fflate`) тянутся с `esm.sh`. Если нужно что-то ещё — согласуй с пользователем, потому что не все регионы имеют к нему доступ.
